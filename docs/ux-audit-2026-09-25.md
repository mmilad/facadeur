# Facadeur editor — UX / maturity audit

**Date:** 2026-09-25  
**Scope:** `@facadeur/editor` shell only (stage chrome, inspector IA, viewport/breakpoint affordances). No product redesign; observations and suggested directions only.  
**Method:** Local `pnpm dev` (Vite, specimen catalog), hands-on walkthrough (project tree, layers, stage pan/zoom, selection, Properties scroll depth, Design → Tokens/Schriften, Specimen page multi-viewport, Base vs viewport override), plus code review of `viewports.ts`, `viewport-bar.tsx`, `panels.tsx`, and stage CSS.

**Reference screenshot (user):** TEXTAREA atom, `control` layer selected, focus mobile · 375, long Bindings stack — attached to the audit request.

**Product direction (Milad, 2026-09-25):** Locked IA below in [Locked product direction](#locked-product-direction-milad-2026-09-25). Supersedes earlier one-line “suggested directions” where they conflict.

---

## Executive summary

The editor’s **data model and multi-viewport rendering are ahead of the shell**: breakpoints rebuild from document/design settings, style and token overrides respect focus + Base/viewport mode, and the specimen page proves side-by-side frames. The **presentation layer still reads as a prototype**: viewport chrome is a bare rounded card with a floating label, the Properties rail is one undifferentiated scroll, and breakpoint **management** exists only as `setBreakpoints` in the core — not in UI.

**Locked direction** reframes fixes around three IA moves: (1) **viewports as first-class Layers (or Layers-adjacent) selections** with a dedicated right-rail “viewport options” mode that does not touch the component tree; (2) **Properties → tab + sub-tab nav** (Content / Style / Layout / Data), distinct from retired global Tokens/Fonts inspector tabs; (3) **left tree → first-class token domain surfaces** (Colors, Fonts, Spacing, …), each a full editor view—not long lists in the narrow right rail. Current duplicate Tokens/Fonts entry points (Design subtree + right tabs) are legacy relative to that target.

## Locked product direction (Milad, 2026-09-25)

These are **decisions**, not options. Implementation details stay open only where noted under [Open questions](#open-questions).

### 1. Viewports via Layers

| Locked                                 | Detail                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Viewport list lives with Layers**    | Each viewport/artboard is a **selectable item** under **Layers**, or in a clearly paired list immediately adjacent to Layers (same left column, shared selection model).                                                                                                                                                       |
| **Two selection modes**                | **Document node** selected → right rail edits node/document properties (tabbed IA below). **Viewport** selected (no node, or explicit viewport row) → right rail edits **viewport options only**.                                                                                                                              |
| **Viewport options (right rail)**      | Outer chrome / wrapper padding; **title in chrome** (not floating above the card); **free numeric inner iframe padding (px, not tokens)**; alignment helpers (e.g. center content in the frame). All **preview/editor chrome**—**must not mutate** the component tree or authored layout tokens.                               |
| **Add / remove viewports**             | Belongs in the **viewport selection flow** (viewport row actions, “+ viewport”, context on selected viewport)—**not** buried in document JSON settings or an invisible settings panel. Wire to existing `setBreakpoints` (and per-page overrides where applicable).                                                            |
| **ViewportEditBar (Base vs override)** | Remains relevant when a **node** is selected and the user edits responsive **style/layout/token overrides**; it is **not** a substitute for viewport chrome settings. Long term, avoid duplicating breakpoint focus in three places (stage click, Layers viewport row, ViewportEditBar)—exact unification is an open question. |

**Maps to audit IDs:** P0-1, P0-2, P0-4, P1-2, P1-3 (implementation path locked; symptoms unchanged).

### 2. Right sidebar IA (node / document properties)

| Locked                    | Detail                                                                                                                                                                                                                                                                                                           |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No single scroll**      | Properties is too dense as one column; ship **primary tab nav** plus **sub-tab nav** where a section is still large.                                                                                                                                                                                             |
| **Proposed primary tabs** | **Content** (identity, text, media, component fields, instance props), **Style** (declarations, variants, states, style block), **Layout** (layout control, spacing, sizing), **Data** (bindings, fields/variants definition when applicable). Sub-tabs TBD per tab (e.g. Style → Base / states / variant axes). |
| **Explicitly not**        | A return of **global** right-rail **Tokens** or **Fonts** tabs—that pattern is retired in favor of left-tree domain surfaces (§3).                                                                                                                                                                               |
| **Right rail scope**      | **Properties + viewport options + (future) nothing else** at the top level of the right column.                                                                                                                                                                                                                  |

**Maps to audit IDs:** P0-3, P1-5, P1-6, P1-12; supersedes P0-3 “sticky TOC only” and P1-5 “reorder only”.

### 3. Left tree — token domains (replace flat Design → Tokens/Fonts)

| Locked                                 | Detail                                                                                                                                                                                                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Replace**                            | Flat **Design → Tokens / Schriften** rows that cram the full token catalog into the **320px** right sidebar.                                                                                                                   |
| **With**                               | **First-class tree entries** per **token domain** (minimum set to plan for: **Colors**, **Fonts**, **Spacing**; extend to match token groups in project template—e.g. radius, shadow, typography scales—as domains stabilize). |
| **Each domain opens**                  | An **individual dedicated view** (full editor surface), not a thin inspector scroll.                                                                                                                                           |
| **Viewport overrides in domain views** | Domain editors should respect the same **focus viewport + Base vs override** model as today’s token panel (global ViewportEditBar or equivalent context in that view)—exact placement is an open question.                     |

#### Recommended hosting for domain views (tradeoffs)

| Surface                                                  | Pros                                                                                              | Cons                                                                                                             | Fit                                                                                                  |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Center stage replaces document preview**               | Maximum width for tables, grids, color ramps; clear “design mode”; matches “full editor surface”. | Loses live component preview until user returns to an asset; need strong breadcrumb (“Colors · project design”). | **Default recommendation** for Colors, Spacing, and other grid-heavy domains.                        |
| **Expanded right panel** (e.g. 480–640px, stage shrinks) | Keeps stage visible for reference; simpler routing than mode switch.                              | Still tight for hundreds of tokens; fights the old failure mode.                                                 | Secondary option for **Fonts** (few rows, high linkage to preview) if stage replacement feels heavy. |
| **Modal / drawer**                                       | Focused editing; quick return.                                                                    | Easy to feel disconnected; poor for long editing sessions.                                                       | **Not recommended** as primary; optional for one-off pickers only.                                   |

**Open:** Whether **Fonts** uses stage replacement or wide panel (see [Open questions](#open-questions)). Colors and Spacing lean **stage replacement** per table above.

**Maps to audit IDs:** P1-1, P1-7, P2-5, P2-6; updates “Out of scope” (Design subtree wording).

## Open questions

Only items **not** locked by Milad:

1. **Persistence model for viewport chrome** (outer padding, inner px inset, title string, alignment): editor session only, per-document `settings`, per-breakpoint sidecar on design file, or hybrid? Must not imply DSL/layout changes.
2. **Layers integration shape:** viewport rows **inside** the same tree as nodes (with visual separator) vs **sibling panel** “Viewports” above Layers—selection mutual exclusion either way.
3. **ViewportEditBar vs viewport selection:** when a node is selected, does Base/override stay in Properties (e.g. Style tab header) while viewport chrome moves to viewport selection only?
4. **Primary tab set for atoms at root:** whether **Content** includes component **Fields/Variants** definition or a fifth top tab **Component** for definition-only blocks.
5. **Fonts domain surface:** stage replacement vs wide right panel (tradeoffs above).
6. **Domain list source of truth:** fixed IA list (Colors, Fonts, Spacing, …) vs dynamic groups from `$extensions` / first path segment—product naming either way.

### Code anchors (P0)

- Stage DOM: `apps/editor/src/viewports.ts` — `viewport-frames` → `viewport-frame` → `viewport-label-slot` + `viewport-screen` → iframe mount.

- Viewport editing: `apps/editor/src/ui/viewport-bar.tsx` — focus copy + Base / viewport toggle only.

## Verified behaviors (keep / working)

- Multi-viewport **synced render** from shared stores; breakpoint rebuild when `page.settings.breakpoints` signature changes (`viewports.ts` tests).
- **Focus viewport** drives `writingBreakpointId` for style, layout, and token overrides (`viewport-edit.ts`, shell test for tablet override + Reset).
- **Design → Tokens / Schriften** opens the correct inspector panel and keeps specimen page open (`shell.test.tsx`).
- **Layers** tree, double-click drill-in to master, drag-from-tree insert rules enforced.
- Canvas **pan/zoom** and stage hint document basic navigation.

## Out of scope / explicit keeps (do not regress)

| Decision                                                                                                                                                                                                   | Rationale                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Token domains live in the left tree** (Colors, Fonts, Spacing, …)—each opens a **dedicated full view** (**§3**). They are **not** global right-rail tabs and **not** a single endless Properties scroll. | Milad direction; retires Design → Tokens/Schriften **and** inspector Tokens/Schriften tabs. |
| **Right-rail top level** is **node/document properties** (tabbed) and **viewport options** when a viewport is selected—nothing else.                                                                       | **§2** + **§1**; Content/Style/Layout/Data tabs are **not** the old Tokens/Fonts pattern.   |
| **Viewport chrome and px inset** are **editor preview** affordances; they **do not mutate** the component tree or replace token-based layout in documents.                                                 | **§1**; P0-2 scope unchanged.                                                               |
| **Node style is always Base** (copy in ViewportEditBar) — viewport mode applies to declarations/layout/tokens on the style owner, not ad-hoc per-node breakpoint nests for every field.                    | Documented product rule; audit does not propose changing the style model.                   |
| **No redesign** of control widgets (color, typography, layout controls) in this audit—only **where** they appear (tabs, domain views, viewport panel).                                                     | Maturity focus is IA and shell; control internals are out of scope.                         |
| **Commands-only breakpoint editing** in JSON remains acceptable for power users until **§1** UI ships.                                                                                                     | P0-4 implementation via Layers/viewport flow, not removal of `setBreakpoints`.              |

## Suggested fix ordering (for implementers)

Aligned with locked direction:

1. **§1 Viewports via Layers** — viewport rows, selection model, right-rail viewport options (chrome, px inset, alignment), add/remove breakpoints (P0-1, P0-2, P0-4).
2. **§2 Right sidebar tabs** — Content / Style / Layout / Data (+ sub-tabs); remove legacy Tokens/Schriften inspector tabs (P0-3, P1-5, P1-6).
3. **§3 Left tree domain surfaces** — replace Design → Tokens/Fonts; stage-first domain editors (P1-1, P1-7).
4. **P0-5 + P1-8–P1-10** — Shell polish (language, zoom, dirty state).
5. **Resolve [open questions](#open-questions)** — persistence for viewport chrome, Fonts hosting, ViewportEditBar placement.

## Appendix — Properties section order (TEXTAREA, `control` node selected)

Observed top-to-bottom in Properties (2026-09-25 build). **Target IA (§2)** maps this into tabs:

| Current block                                  | Target tab                                                                 |
| ---------------------------------------------- | -------------------------------------------------------------------------- |
| ViewportEditBar                                | **Style** (or global bar above tabs when node selected—see open questions) |
| Node id, Type, Document, Name, Tag, attributes | **Content**                                                                |
| Bindings                                       | **Data**                                                                   |
| Variant styles, Style, StyleFields             | **Style** (sub-tabs: variants / declarations)                              |
| Layout                                         | **Layout**                                                                 |

Legacy order (unchanged in app today):

1. ViewportEditBar (focus + Base / mobile is Base)
2. Node id (`control`)
3. Type / Document kv
4. Name, Tag
5. Attribute fields (`readonly`, `tabindex`)
6. **Bindings**
7. **Variant styles** (if variants defined — axis layers)
8. **Style** (style block declarations for node — atoms use root style block paths)
9. Per-node **style property fields** (`StyleFields`)
10. **Layout**

Root selection additionally inserts **Fields**, **Variants**, **Component** style block sections above or among node sections — map to **Data** / **Style** / **Content** per open question on component definition.
